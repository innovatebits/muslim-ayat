## Executive summary

Muslim Ayat already has a functioning public Quran reader, source-aware Quran data package, Arabic/translation/transliteration search, on-demand tafsir and word-by-word study, basic ayah recitation, sign-in-gated personal records, IndexedDB and Supabase synchronization, and a PWA cache path. Its current Next.js/TypeScript, Supabase, IndexedDB, PWA, and Cloudflare design is appropriate; no reference project justifies replacing it or adding a new package now.

The outstanding work is targeted: verify content rights (including Juz boundary data), and keep study-resource offline access blocked until the relevant rights explicitly permit offline caching. Juz navigation, improved local Arabic search, and the core public-reader offline path are implemented; their current status is reflected below. Reader themes/comfort await design and accessibility review. A reading goal/Khatma is conditional on explicit product approval and a separately reviewed authenticated persistence/RLS design. Ummah Library’s pure-domain algorithms and Bayaan Web’s player/reader behavior are useful **design references**, but both reference repositories are AGPL-licensed. Do not copy their code or redistribute their datasets absent a deliberate license and rights review. Hifz, worship, social, playlists, and LMS-like features are not recommendations for Muslim Ayat.

## Scope and evidence

- This audit inspected Muslim Ayat source, package manifests, tests, service worker, Next.js headers, and database migrations—not only project descriptions.
- Reference claims were checked against files at the pinned commits above. File paths below are relative to each repository.

The later implementation-status refresh is documentation-only and does not change application behavior.

Every flag defaults to **enabled** when unset; only the case-insensitive exact string `false` disables it. `.env.example` explicitly sets all listed flags to `true`. ### Persistence, synchronization, and access boundaries

- `apps/web/src/lib/offline/repository.ts` stores personal data in IndexedDB stores `bookmarks`, `notes`, `progress`, and `outbox`; its v2 migration removes the unused `publicQuran` store. Personal records and outbox operations are partitioned by `ownerId`; deletes use tombstones and repeated edits are coalesced.
- `apps/web/src/lib/offline/sync.ts` verifies the active Supabase user matches the owner before syncing; it validates queued operations, replays stable operation IDs, merges remote records by timestamp then operation ID, and pulls bookmarks, notes, and progress.
- `apps/web/src/components/quran/PersonalAyahControls.tsx` prompts unauthenticated users before bookmark, note, or progress saves. `apps/web/src/app/actions/personal-data.ts` also authenticates and validates account mutations. `getPersonalData()` returns empty private data when signed out.
- Profile preference and reader-preference changes remain usable on-device without an account. Reader preferences sync to Supabase only for signed-in users; this does not gate reading.
- `apps/web/public/sw.js` caches public reader routes/assets only. The study handler (`apps/web/src/app/api/study/[surahNumber]/[ayahNumber]/route.ts`) has no auth requirement and sets public cache headers, but `/api/study` is not currently handled by the worker’s caching branches.

### UI, responsive behavior, accessibility, and tests

- The app uses Tailwind CSS and a small set of CSS variables/focus styles in `apps/web/src/app/globals.css`; the theme is currently light-only. Reader behavior is concentrated in `apps/web/src/components/quran/SurahReader.tsx`, preferences in `ReaderPreferences.tsx`/`ReaderSettings.tsx`, study in `StudyAid.tsx`, and audio in `apps/web/src/components/audio/AyahAudioPlayer.tsx`.
- Pages use responsive Tailwind layouts, semantic headings/nav/forms, Arabic `lang="ar"`/`dir="rtl"`, focus-visible outlines, and reduced-motion CSS. `apps/web/e2e/home.spec.ts` checks guest reading, narrow-screen reader layout, focus, source disclosures, and PWA manifest icons.
- Tests include data/schema and import validation (`packages/quran-data/src/{index,companions,metadata,qul,reader,study,study-import,audio}.test.ts`), feature defaults (`apps/web/src/lib/features.test.ts`), auth helpers, offline repository/sync tests, and database RLS tests. `.github/workflows/ci.yml` runs typecheck, lint, unit/e2e tests, build, migration lint, and RLS tests.
- Remaining gaps: rights for source resources, including Juz boundaries, remain unknown; study API and audio are not available offline; there is no personal learning-history model; and `features.test.ts` does not cover the `false` environment override. Search normalization/ranking and public-reader cache/fallback behavior now have tests.

## Ummah Library: source review and reuse assessment

Ummah Library is a broad multi-client platform, not a drop-in Quran package. Its documented monorepo separates pure `packages/core` logic, `packages/data` datasets/ingestion, `packages/adapters` persistence, UI primitives/themes, and web/mobile apps. Its local-first decision (`docs/adr/0006-local-first-persistence.md`) keeps private state on-device without accounts; that is deliberately different from Muslim Ayat’s sign-in requirement for personal saves and learning history.

| Capability and verified source | What the source does | Muslim Ayat disposition |
|---|---|---|

## Licensing, data rights, and attribution

### Repository code licenses

- Muslim Ayat’s root `LICENSE` is MIT.
- Ummah Library’s root `LICENSE` is GNU AGPL version 3.
- Bayaan Web’s `LICENSE` and `package.json` declare AGPL-3.0-or-later.
- Do not copy their code into Muslim Ayat as part of this audit. Direct reuse could impose AGPL obligations on a combined/derivative distribution and affect the intended MIT licensing; obtain legal advice before considering any exception. Architectural ideas and independently written implementations are the lower-risk path.

Muslim Ayat’s source registry and `ContentSources.tsx` already expose source, edition, rights status, notes, and URLs; `scripts/validate-quran-data.ts` checks structure and source checksum. These safeguards are valuable but do not clear rights. The public QUL FAQ itself says rights vary by resource and directs users to resource-specific terms. Bayaan’s current-state docs identify Quran.com and Bayaan/MP3Quran-related services as separate content sources; Bayaan’s [Terms](https://thebayaan.com/terms) state external audio is subject to provider terms and that some exclusive recordings are owned by reciters with distribution permission. Those statements do not grant rights to Muslim Ayat or to unrelated recordings. Quran Foundation’s [API FAQ](https://api-docs.quran.com/docs/tutorials/faq) likewise notes rights-holder/licensing terms vary by translation and recitation.

Ummah Library’s `packages/data/ATTRIBUTION.md` is a useful per-dataset documentation example: it attributes Tanzil Uthmani with CC BY 3.0 notice requirements and separates other datasets/rights; it also states its plugin tafsir editions remain copyrighted and does not bundle streamed recitations. That is evidence about Ummah’s own files, not a license for Muslim Ayat to import them. QUL’s [FAQ](https://qul.tarteel.ai/faq) says resource rights vary and directs users to resource-specific terms; AlQuran Cloud’s [CDN documentation](https://alquran.cloud/cdn) describes delivery, not a blanket grant to redistribute recordings.

### Dependency licenses

No reference dependency is adopted or recommended. Bayaan’s `package.json` lists distinct direct dependencies including Fuse.js, Zustand, Base UI, dnd-kit, and shadcn; the manifest is not a complete license inventory. Ummah’s Hifz and plugin domain modules are pure TypeScript, but that does not make the entire repository or its datasets MIT-licensed. A resolved-version/transitive dependency license audit was not performed because this roadmap adds no dependencies. If a specific package is considered later, inspect its exact resolved version, license, transitive notices, and distribution obligations separately from the repository’s AGPL code license.

## Architecture proposal: extend existing boundaries

1. **Quran domain (`packages/quran`).** Keep pure concepts that do not need I/O in this existing small package. Juz boundaries/helpers and search normalization/ranking are implemented; deterministic reading-goal calculations remain conditional on approval. Make time and data inputs explicit. Do not put source text, Supabase clients, UI components, or network calls here.
2. **Content and provenance (`packages/quran-data`).** Keep canonical corpus, translations/tafsir/glosses, audio manifests, source metadata, importers, checksums, and schema/coverage validation here. Separate each resource and its rights status. Continue deriving data from reviewed sources; do not normalize or generate Quran text.
3. **Study domain.** Start in the existing `packages/quran` boundary for pure learning/reading-progress rules; keep presentation in `apps/web/src/components/quran/StudyAid.tsx` and route composition in the app. Avoid a new “study” package until a second client needs the same independent domain API.
4. **Personal data.** Keep account-owned bookmarks, notes, progress, and future learning history separate from public Quran content. Reuse `packages/shared` for cross-layer input/sync schemas and `packages/database` for database types. Any future history schema/RLS work requires a separately approved migration; none is proposed or changed here.
5. **Persistence adapters.** Keep IndexedDB, outbox, Supabase RPC, and auth ownership checks in `apps/web/src/lib/offline/` and Supabase integration. If another client appears, extract a genuine shared port/adapter boundary then; do not import Ummah’s no-account local-first policy.
6. **UI/presentation.** Keep Next.js routes and reader components in `apps/web`; use the existing CSS variables and `packages/ui` primitive. Promote primitives only when multiple Muslim Ayat screens consume them. Preserve server-rendered public reading, unauthenticated search/study/audio, and separate private responses/caches.
7. **Architecture decision rule.** No new package, backend, search service, state library, or design system is warranted by this audit. Add one only for a clear consumer/boundary need. No reference code or data should be copied in the interim.
